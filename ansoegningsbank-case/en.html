Case 04 · Side project

I built a tool that writes job applications from what you have actually done, and never makes anything up

The Application Bank turns the application around. Instead of writing from scratch every time, you build a bank once: your experience, results and tools, each entry with a source. When you find a job, you paste the posting. The tool reads the requirements, shows what you cover and what you lack, and writes a draft only once you have decided to apply. Every sentence in the draft points back to an entry in your bank, and numbers that are not in it never make it in. The same works for small associations and cultural organisations applying for grants.

01 · The idea

The idea was to make an application something you build from facts, instead of something you write from scratch every time

Every application normally starts at zero. You retell your experience in new words, forget the concrete numbers and results, and are tempted to embellish a little because the posting asks for something you have only half done. AI tools make it faster, but not more honest: they write beautifully about things you have never done, and an application that cannot survive an interview is worse than none.

The Application Bank is built on a different order. First you make your bank: a list of entries, each one a single concrete fact with a source, for example Account manager at Nordfjord Regnskab, 40 regular clients, 2021 to 2023, evidence: employment contract. The bank is built from a CV, a portfolio or earlier applications, or by answering one question at a time. Every suggested entry has to be approved by the user before it may be used. Then you paste a job posting. The tool finds the posting’s requirements, compares them with the bank and shows in plain language what you cover, what is unclear and what you lack. Then you decide for yourself whether to apply. Only then is the draft written, in the user’s own tone, and every sentence in it can be traced back to an entry in the bank. Before you copy the text, you read each claim next to the source’s own wording. An exaggeration becomes visible without looking anything up.

The tool is built for two kinds of users: job seekers and students applying for jobs and student jobs, and small organisations such as associations and record labels applying for grants and funds. It is the same core with two different templates. Three principles apply to both: everything in a draft has a source; the human makes every decision and sends it themselves; and the structure is the product, so the user never has to phrase an instruction to an AI.

The idea is not new to me. It generalises a tool I built earlier for one particular job seeker, where the principle of a bank and a fact check was tried on real applications. This version is written from scratch so that no requirement, no rule and no code is made for one person.

02 · How it fits together

How it fits together: the bank is built once, and every application follows the same five steps

The bank is the foundation, and it grows with every application: every gap you answer becomes a new entry. The application itself always follows five visible steps, so at any moment you can see where you are, what to do now, and what happens when you press.

The bankentries with source and status, built from CV, portfolio, questions and answers to gaps
→
1 · Postingtext, PDF or link; the tool guesses the type, job or grant, and the guess can be corrected
→
2 · Checkyour own conditions first, then the posting’s requirements, match and gaps
→
3 · Decisionyes, I apply; not yet, I need an answer; or no
→
4 · Draftwritten, validated and fact-checked; copy or download as Word once everything is checked

The fifth step is the outcome: once the draft is marked as sent, it is locked with a snapshot of the entries it was built on, so later edits in the bank never change the documentation of an old application. The outcome is recorded in fixed categories, from "sent, no reply" to "offer" or "granted", and once there are enough applications the tool shows patterns, for instance that the applications that led to an interview all had a match above 70.

03 · The stack

The technology: a pure Python core that knows nothing about the screen, a thin web interface and one database file

Most software is split into three layers: what the user sees, the rules that decide what may happen, and the data that has to be right no matter what. Here the rules are deliberately placed in a core that does not know a web interface exists. That makes it possible to test every rule without a browser and to replace the screen layer later. PythonThe programming language across the whole project: the core, the web layer and the tests.The honesty rules are text processing and lists, and Python is good at that. The core of the earlier tool was Python too, so it could be generalised rather than rewritten in another language.
FastAPIA small web framework that receives forms and sends pages back.Thin enough to be a pure layer on top of the core: every page is a function that calls the core and renders an answer. No magic, and easy to test with a built-in test client.

SQLiteA database that lives in one file on the computer instead of on a server.Version 1 runs locally for one account. One file means a backup is a copy of the file, and no personal data leaves the computer. Numbered migrations let the schema evolve without losing data.
Claude API with structured outputAnthropic’s AI model, called with a fixed answer format (a JSON schema), so the answer always has exactly the fields the code expects.A free-text answer would require guessing where the requirements or source IDs are. With a schema the answer is data from the first line, and errors from the service are translated into plain Danish messages. The model is chosen in configuration, not in code.
pypdf and python-docxTwo small libraries: one reads text out of PDF files, the other writes Word files.Postings and CVs arrive as PDF, and a finished application has to be delivered as Word. The files themselves are never stored; only the text.

06 · The timeline

The timeline: four working days, where the documentation came first and using the tool steered the rest

The project was built in four sessions over one week. The code history is the timeline: 54 saved changes from 29 September to 5 October, each tagged with the number of the task in the plan it completed.

29 September
Day 1: the documents first, then the coreThe day began with five documents: 22 requirements, a design standard with a glossary from system words to user words, an architecture with a data model, the writing rules for the model, and a task list. Then the whole core was built with tests from the start: database, bank, your conditions with an amount check, honesty rules, analysis, the job template, decisions and outcomes. By the end, the whole flow ran from the command line on a fictional posting.
30 September
Day 2: a web interface rather than StreamlitThe choice fell on a real web app with FastAPI and server-rendered pages, because background jobs, locked sent drafts and the fact check with sources needed more control than a quicker tool would give. The first visit, My bank and the five steps were built in one session.
4 October
Day 3: a review from eight angles and the extension to grantsEvery page was reviewed for language, accessibility, spacing and clutter: 110 findings became 24 changes to the design system and fixes on 15 pages. The fonts were stored locally, errors now appear at the field they belong to, and nothing is lost on an error. The same day brought projects for organisations, the grant template with the fund’s own form fields and character limits, 14 fund profiles and the first patterns from outcome tracking.
5 October
Day 4: first real use, and everything that felt heavyThe tool was used on real job postings, and ten findings were fixed in three rounds the same day: waiting pages that show what is happening, answers to gaps without a reload, clearer choices on Decision, document types beyond the CV. On top of that came login with invitations and credits, CSRF protection, a quality framework built on Danish guides to good applications, and a warmer design, "Cobalt on paper", after the first one felt flat. In the evening, a final review of every screen with five small fixes.

07 · Limits and trade-offs

Limits: what the tool deliberately does not do yet

It runs on my own computer, not on the web

Login, invitations, credits and CSRF protection are built so the tool can be opened to others. What is missing is operations: a server with HTTPS in front, a daily backup of the database, and a plan for what it may cost in model calls. Until then it is a tool for me and the people I sit next to.

The grant part is built, but not yet tried on a real application

The template follows the fund’s structure, answers the assessment criteria one by one and keeps within the character limits, and 19 profiles are ready. But the first real grant application, for a record label, is waiting for a round to open. Only then will I know whether the template holds.

A check takes up to a minute

The model reads the whole posting every time, and that takes time. The tool does not hide it behind a spinner but shows the steps and lets the user leave the page. Faster would require a smaller model or skipping the requirement extraction, and both would cost honesty.

The tool is only as good as the bank

A thin bank gives "unclear" on most things, and that is deliberate: the tool never guesses that you can do something. It also means the first application is the heaviest. The goal is under fifteen minutes from sign-up to the first check with a CV, and that has not yet been measured on a stranger.
