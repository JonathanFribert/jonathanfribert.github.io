Case 04 · Side project

The Application Bank writes job applications from what you have actually done, and never makes anything up

The Application Bank is a tool I built to make it easier to apply for jobs without embellishing and without starting from zero every time. You gather your experience, results and skills in one place, with a source behind every entry. When you find a posting, the tool shows you what you cover and what you lack. Once you have decided to apply, it writes a draft in which every sentence can be traced back to something you have done. The same core helps associations and cultural organisations apply for grants.

01 · The idea

Why an application should be built from facts instead of being written from scratch every time

Most applications start at zero. You retell your experience in new words, forget the concrete numbers and are tempted to embellish, because the posting asks for something you have only half tried. AI tools make it faster, but not more honest, because they write just as well about things you have never done. The purpose of the Application Bank is to reverse the order. First you gather facts, then you assess the posting, then you decide, and only then is any text written.

02 · The bank

The bank is made of small, concrete facts about you, and every entry has a source

An entry in the bank is not a paragraph from a CV. It is one fact you can stand behind: what you did, where, when, and what it led to. Every entry has a short ID that drafts refer to, and a status that decides whether it may be used.

03 · The workflow

Five steps from job posting to sent application

Every application follows the same five steps, so you can always see where you are, what to do now, and what happens when you press a button. The figure shows what you do yourself, what the tool works out with fixed rules, and when the AI model is involved.

04 · Honesty

How the draft is kept honest

The model only gets your confirmed entries, the posting and the tone you have chosen. But a reference to an entry does not prove that the claim is right. "Took part in a project with 20 participants" must not become "led a team of 20", even though both the entry and the number exist. So fixed checks run after the model has written, and at the end you do a fact check yourself.

05 · The stack

How the tool is built

All the rules live in a core that does not know a web interface exists. That makes it possible to test every rule without a browser and to replace the screen layer later. The check script refuses to approve a change if the core imports anything from the screen layer.

The main technical choices, and why they were made

ToolWhat it isWhy it was chosen
PythonThe programming language for the whole project: the core, the web layer and the tests.The honesty rules are text processing and lists, and Python is good at that. The core of the earlier tool was also Python, so it could be generalised instead of rewritten.
FastAPIA small web framework that receives forms and sends pages back.It is thin enough to be a pure layer on top of the core: every page is a function that calls the core and renders a response. It is easy to test with a built-in test client.
Jinja2 instead of ReactTemplates that become finished HTML on the server before the page is sent to the browser.There is no build step and no packages to maintain, and the pages work without JavaScript. A tool you read and fill in does not need to be an app.
SQLiteA database that lives in one file on the computer instead of on a server.Version 1 runs locally for one account. A backup is a copy of the file, and no personal data leaves the computer. Numbered migrations evolve the database without losing data.
Claude API with structured outputAnthropic’s AI model, called with a fixed response format (a JSON schema), so the answer always has exactly the fields the code expects.A free-text answer would require guessing where the requirements or source references are. With a schema the answer is data from the first line. The model is chosen in the configuration, not in the code.
pypdf and python-docxTwo small libraries: one reads text out of PDF files, the other writes Word files.Postings and CVs arrive as PDF, and a finished application has to be delivered as Word. The files themselves are never stored, only the text.
pytest and check.sh137 automated tests and a script with nine checks of what tests do not cover.Among other things the script checks that the app only listens on the local machine, that no keys, databases or CVs have ended up in Git, that the core imports nothing from the screen layer, and that there are no dashes in the user interface.
Local fonts, nothing from outsideThe fonts Fraunces and Manrope live in the project, and the pages fetch nothing from other domains.The footer promises "Everything stays on this computer", and that has to apply to the fonts too. The tool should not tell anyone that you are looking for a job.
Login, invitations and creditsAccounts with passwords, invitation codes from an admin page, and a price in credits for every use of the AI model.It is built so the tool can be opened to others later without paying for strangers’ use of the model. Five actions cost credits, the balance is always visible, and when the balance is zero the button does not call the model.

08 · The timeline

Four working days from the first document to a tool in use

The project was built in four sessions over a week. The code history is the timeline: 54 saved changes from 29 September to 5 October, each tagged with the number of the task in the plan it completed. The documentation came first, and using the tool steered the rest.

29 September
Day 1 · The documents first, then the coreThe day began with five documents: 22 requirements, a design standard with a glossary from system words to user words, an architecture with a data model, the writing rules for the model, and a task list. Then the whole core was built with tests from the start, and the whole flow was run from the command line on a fictional posting.
30 September
Day 2 · A real web app rather than a quick prototyping toolThe choice fell on a web app with server-rendered pages instead of a prototyping tool like Streamlit. Background jobs, locked sent drafts and the fact check with sources needed more control than a quicker tool would give. The first visit, My bank and the five steps were built in one session.
4 October
Day 3 · A review from eight angles and the extension to grantsA review of every screen from eight angles produced 110 findings, which became 24 changes to the design system and fixes on 15 pages. The fonts were stored locally, errors now appear at the field they belong to, and nothing is lost on an error. The same day brought projects for organisations, the grant template with the fund’s own form fields, 14 fund profiles and the first patterns from outcome tracking.
5 October
Day 4 · The first real use, and everything that felt heavyTen findings from real postings were fixed in three rounds the same day. On top of that came login with invitations and credits, protection against forged form submissions, the quality framework from Danish guides, and the warmer design "Cobalt on paper". In the evening a final review of every screen followed, with five small fixes.

09 · Limits and trade-offs

What the tool does not do yet

It runs on my own computer, not on the web

Login, invitations, credits and protection against forged form submissions are built so the tool can be opened to others. What is missing is operations: a server with HTTPS in front, a daily backup of the database, and a plan for what the use of the AI model may cost.

The grant part is built, but not yet tried on a real application

The template follows the fund’s structure, answers the assessment criteria one by one and keeps within the character limits, and 19 profiles are ready. The first real grant application is waiting for a round to open.

A check takes up to a minute

The model reads the whole posting every time. The tool does not hide that behind a spinner but shows the steps and lets you leave the page. Faster would mean skipping the requirement extraction, and that would cost honesty.

The tool is only as good as the bank

A thin bank gives "unclear" on most things, and that is deliberate: the tool never guesses that you can do something. The first application is therefore the heaviest. The goal is under fifteen minutes from sign-up to the first check with a CV.
